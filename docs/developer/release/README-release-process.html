Release Process: Annotation File Utilities, Checker Framework

This document explains how to make a release of the Checker Framework and the Annotation File Utilities. The process takes around 2 hours (including manual steps) when all goes according to plan. However, the lengthiest steps are automatic so you will be able to work on other tasks.

Note: If you have never read this document before, please read the section Pre-release Checklist first. It is also recommended that you read sections Release Process Overview and Changelog Guidelines to familiarize yourself with the process.

Step by Step

More information about the steps appears in code comments in the release_build.py and release_push.py scripts.

Answering 'no' to a prompt does not exit the script unless otherwise indicated.

  1. If you have never made a release before, follow the instructions in the Pre-release Checklist.
  2. Browse to https://github.com/eisop/checker-framework/security/dependabot and if there are any reports, try to update the responsible packages.
  3. On your own computer, update the Checker Framework source code in the master branch:
    • Update the Checker Framework change log, which also covers the Annotation File Utilities, by following the instructions at content guidelines. Leave the date in the heading of the release's section, ## Version VERSION (DATE), as it is: release_build sets it to the release date, the date in UTC, as in the rest of the documentation.
    • Update the Checker Framework version number in checker-framework/release.gradle, in the ext block: set releaseVersion to the version being released, such as 1.2.3-eisop4, without -SNAPSHOT. (Usually it already is: release_push opens a pull request that sets it to the next release after each release.) The build's version is releaseVersion when Gradle is run with -Prelease=true, as the release scripts do, and releaseVersion followed by -SNAPSHOT otherwise.

      Update the minor version (middle number in the version number) if there are any incompatibilities with the previous version. This includes incompatibilities for people who are maintaining a checker, which happens if the signature changes for any method in these classes: 

      AnnotatedTypeFactory
BaseAnnotatedTypeFactory
GenericAnnotatedTypeFactory
CFTransfer
CFAbstractTransfer
CFAbstractAnalysis
CFAnalysis
CFAbstractStore
CFStore
CFAbstractValue
CFValue
BaseTypeVisitor
BaseTypeChecker
SourceChecker
AbstractQualifierPolymorphism
AnnotationUtils
TreeAnnotator

      (TODO: Write a command that diffs these classes between the previous and current release.)

      A rule of thumb is that any framework change that requires changes to more than one type-checker should be at least a minor version (middle number in the version number) bump.

    • Commit and push these changes to eisop/master.
  4. Use JDK 21 or later. release_vars.py sets JAVA_HOME to $JAVA_21_HOME, by default /usr/lib/jvm/java-21-openjdk/. The framework-errorprone subproject (the Checker Framework as an Error Prone plugin) is part of the build only on JDK 21 or later (it is gated in settings.gradle), so release_build checks the JDK's version.
  5. Check your setup on the machine that runs the release. Do this even if you have released before, especially on a new machine. It needs, as in the Pre-release Checklist:
    • signing.gnupg.keyName, SONATYPE_NEXUS_USERNAME, and SONATYPE_NEXUS_PASSWORD in ~/.gradle/gradle.properties, and the secret key in gpg, with its current public key on keyserver.ubuntu.com;
    • permission to push to git@github.com:eisop/checker-framework.git, and git config user.name and user.email;
    • JDK 21 or later at $JAVA_21_HOME;
    • gh, logged in with gh auth login, which posts the GitHub release and publishes the web site.
    release_build checks all of these in its step 2, before the build, and stops if one is missing; gpg may ask for your passphrase there.
  6. In a user-specific temporary directory, clone/update the Checker Framework repository (it contains the release scripts).
    mkdir -p /tmp/$USER/cf-release
     cd /tmp/$USER/cf-release
     test -d checker-framework && (cd checker-framework && git pull --ff-only --quiet) || git clone --quiet https://github.com/eisop/checker-framework.git
     cd checker-framework/docs/developer/release
     To use another directory, set the environment variable CF_RELEASE_DIR to it before running the release scripts.
  7. Run release_build to build the release in a clone, commit it, and tag it. It does not push anything; nothing is on GitHub yet.
    git pull && python3 release_build.py

    --dry-run builds the clone of the release scripts unattended, without credentials: it answers every question with its default and skips the checks of the signing key, the Maven Central token, and access to GitHub. CI runs it, followed by release_push.py --dry-run; see checker/bin-devel/test-release.sh.

    Note: release_build deploys the release to your local Maven repository (for the Maven sanity check in release_push) with -Prelease=true, which signs the artifacts. Set up your signing key, as for the Maven Central publish step below, before running it.

    If release_build fails, fix the problem and run it again. It resets build/checker-framework to master, discarding the release commit and tag of the failed run, and it retries the downloads, which it does before committing the release. If the clone holds anything else that the reset would discard, such as a fix you made by hand, a commit, or a stash, it lists it and asks first. Both scripts stop if another user could change /tmp/$USER/cf-release.
  8. Run release_push to test the release, push it to GitHub, and guide you through the manual steps
    python3 release_push.py release

    The "release" argument states that you intend to do an actual release. If you just want to test the script, leave out "release" and the script will run its checks and prompts but will not push or post anything.

    Before anything is public, the script uploads the Maven artifacts to Maven Central and waits until they are validated. Pushing master and the tag to GitHub (step 6) is the first irreversible step; answering "no" there stops the script. Afterwards the script asks before it publishes the Maven artifacts on Maven Central, before it posts the GitHub release with the two zip files attached, from which the web site is generated, and before it starts publishing the web site. If the script stops, for any reason, run it again: it skips the steps that are done. See Release Scripts for all steps.

  9. Publish to Maven Central. release_push.py does this in steps 5 and 7: it checks the artifacts that release_build.py published to the local Maven repository again, uploads exactly those files, waits until the Central Portal has validated them, and asks before it publishes them. If you decline or a step fails, do it by hand, on the machine that ran release_build.py: upload /tmp/$USER/cf-release/central-bundle-VERSION.zip at https://central.sonatype.com/publishing/deployments with "Publish Component", wait until the deployment is VALIDATED, and click Publish. See Maven Central publishing.

Continuous integration tests

The CI workflow, ci.yml, must pass on master before a release. release_build checks that it passed on the commit that it releases, and release_push checks it again before it runs the tests. Its release job runs the release scripts as a dry run (see checker/bin-devel/test-release.sh), so a problem in them shows up in a pull request.

Deploy to local Maven repository

To deploy to a local Maven repository, run ./gradlew PublishToMavenLocal in checker-framework.

Then, update your project's buildfile. For Maven, just update the Checker Framework version number. For Gradle, also add repositories { mavenLocal() }.

Unless you pass -Prelease=true, the version number is releaseVersion from checker-framework/release.gradle followed by -SNAPSHOT. Regardless of the version number, beware that you may get different results than on other computers that have not deployed the same commit of the Checker Framework to their local Maven repository.

Snapshot release

To release the Maven artifacts to the Maven Central snapshot repository:

  1. Ensure that ~/.gradle/gradle.properties includes your user token in SONATYPE_NEXUS_USERNAME and your user token key in SONATYPE_NEXUS_PASSWORD.
  2. Run ./gradlew publish in checker-framework, without -Prelease=true, so that the version is releaseVersion from release.gradle followed by -SNAPSHOT. (The Publish snapshot GitHub workflow does this daily.)

Using a snapshot release

Gradle Groovy (build.gradle file)

In the build.gradle file of a project that you want to use the snapshot version of the Checker Framework: 
repositories {
  ...
  maven { url 'https://central.sonatype.com/repository/maven-snapshots/' }
}

ext.checkerFrameworkVersion = '3.42.0-eisop5-SNAPSHOT'
dependencies {
  compileOnly "io.github.eisop:checker-qual:${checkerFrameworkVersion}"
  testCompileOnly "io.github.eisop:checker-qual:${checkerFrameworkVersion}"
  checkerFramework "io.github.eisop:checker-qual:${checkerFrameworkVersion}"
  checkerFramework "io.github.eisop:checker:${checkerFrameworkVersion}"
}
configurations.all {
  resolutionStrategy.cacheChangingModulesFor 0, 'seconds'
}

Gradle Kotlin (build.gradle.kts file)

In the build.gradle.kts file of a project that you want to use the snapshot version of the Checker Framework: 
val checkerFrameworkVersion = "3.42.0-eisop5-SNAPSHOT"
dependencies {
   compileOnly("io.github.eisop:checker-qual:${checkerFrameworkVersion}")
   testCompileOnly("io.github.eisop:checker-qual:${checkerFrameworkVersion}")
   checkerFramework("io.github.eisop:checker-qual:${checkerFrameworkVersion}")
   checkerFramework("io.github.eisop:checker:${checkerFrameworkVersion}")
}
configurations.all({
   resolutionStrategy.cacheChangingModulesFor(0, "seconds")
})

Maven (pom.xml file)

In the pom.xml file of a project that you want to use the snapshot version of the Checker Framework: 
    <repository>
      <id>snapshots-repo</id>
      <url>https://central.sonatype.com/repository/maven-snapshots</url>
      <releases><enabled>false</enabled></releases>
      <snapshots><enabled>true</enabled></snapshots>
    </repository>

Pre-release Checklist

If you have not performed a release before you must follow these steps.

1. Set up a PGP signing key
Maven Central requires signed artifacts, but does not pin a key to a namespace: each maintainer signs with their own. Have a GPG key whose public half is published to a keyserver Central queries (keys.openpgp.org or keyserver.ubuntu.com), and upload it again whenever you extend its expiry date: users who verify the signatures fetch the key from there. release_build checks the copy on keyserver.ubuntu.com. Name the key in ~/.gradle/gradle.properties:
signing.gnupg.keyName=your_key_id_or_email
release_build asks gpg for the passphrase in its step 2, and signs the artifacts hours later, at the end of its build. So that gpg-agent still has the passphrase then, set default-cache-ttl 28800 and max-cache-ttl 28800 in ~/.gnupg/gpg-agent.conf (then run gpgconf --kill gpg-agent), and export GPG_TTY=$(tty) in the shell that runs the release. See Maven Central publishing.
2. Get publishing rights for io.github.eisop on Maven Central
Create an account on the Central Portal, and ask a maintainer who already publishes to add you to the io.github.eisop namespace; if that does not work, ask Central support. Do this a few days in advance.
3. Add your user token to ~/.gradle/gradle.properties.
Follow the instructions to generate a user token. Create a ~/.gradle/gradle.properties file with the following: 
SONATYPE_NEXUS_USERNAME=your_tokenuser
SONATYPE_NEXUS_PASSWORD=your_tokenkey
Since the file contains your password, make it non-readable: chmod og-rw ~/.gradle/gradle.properties
4. Get push access to the Checker Framework
You should be listed as a member of eisop as a committer on GitHub: release_push pushes the release commit and tag to master.
5. Add a GitHub SSH key on the machine that runs the release
See GitHub docs. Also install gh and log in with gh auth login: release_push posts the GitHub release and publishes the web site with it.
6. Configure git
git config --global user.name "Your Name"
git config --global user.email you@example.com
or copy over your configuration file.
7. Clone the Checker Framework
mkdir -p /tmp/$USER/cf-release
cd /tmp/$USER/cf-release
git clone git@github.com:eisop/checker-framework.git checker-framework
If the directory already exists, the git clone command will fail. That is OK.
8. Run release_build.py once
To save time on release day addressing potential configuration issues, before your first release day, ensure that release_build.py is working correctly by following the initial steps of the Step by Step section. release_build.py still needs to be re-run on release day (even if no changes were pushed to any repositories since the last run of release_build.py) in order for the release date to be correct in all documents. It discards the release commit and tag of the earlier run. 
cd /tmp/$USER/cf-release/checker-framework/docs/developer/release
python3 release_build.py

Release Process Overview

This section first explains the structure of the projects on disk and then lists scripts used during the release process.

File Layout

Release Directory
/tmp/$USER/cf-release (or $CF_RELEASE_DIR) Contains the clones and files used to perform a release
checker-framework/docs/developer/release The directory where the release scripts are run from. Any changes made under this directory won't be automatically committed when the release is committed.
build/checker-framework The clone in which release_build builds, commits, and tags the release. release_push pushes master and the tag from it.
build/jdk A shallow clone of the annotated JDK, which the build reads.
release-files The two release zip files, checker-framework-VERSION.zip and annotation-file-utilities-VERSION.zip. release_push attaches them to the GitHub release.
sanity Directory used by the release_push script to do sanity checks.

The site https://eisop.github.io/ is generated by the "Publish website" GitHub Actions workflow of the repository eisop/eisop.github.io, daily at 20:00 UTC or when the workflow is dispatched manually, from the two zip files attached to the GitHub release. The development version of the site, https://eisop.github.io/cf/dev/, is generated the same way from the zip files that the nightly-zips job of CI (.github/workflows/ci.yml) attaches to the nightly prerelease after the daily scheduled run of master passes. It shows the manual and the zip files of the next release as they are now; the prerelease is not a release, and GitHub's "latest release", which the release scripts read, excludes it.

Release Scripts

To release the Checker Framework you run two scripts, release_build.py and release_push.py. Both are documented in code comments, and have supporting scripts and files in the release directory.

release_build.py Builds the release in build/checker-framework, commits it, and tags it, without pushing. Steps:
  1. Clone the repository and the annotated JDK, or reset existing clones to master, after asking if that would discard work other than a release commit.
  2. Check that the required tools are installed, that the JDK is 21 or later, that gpg can sign with your key and the key on keyserver.ubuntu.com verifies the signature, that Maven Central accepts your token, and that you can push to GitHub.
  3. Download the dependencies, trying up to three times.
  4. Determine the versions: the latest GitHub release and releaseVersion, which must be greater, and which master must have, too; its tag must not be on GitHub yet.
  5. Update the version numbers: updateVersionNumbers. Set the date of the release's changelog section, and reflow its "Closed issues" list into filled lines.
  6. Commit the release, and tag it with an annotated tag, signed with your key, that records the commit of the annotated JDK.
  7. Build: buildAll, the tutorial, ./gradlew zip annotationFileUtilitiesZip -Prelease=true; copy both zip files to release-files; run check-release-links.py --online on the unpacked zip; publishToMavenLocal, and check the artifacts there (see Maven Central publishing). Every Gradle command uses the annotated JDK of step 1, without updating it.
release_push.py Tests the release, publishes it, and guides you through the remaining steps. Run it on the machine that ran release_build.py. It asks before each public or irreversible step, with "no" as the default for the push, the publish on Maven Central, and the GitHub release. If it stops, run it again: it skips the steps that are done. Steps:
  1. Check that the new version is greater than the latest release, and that master on GitHub has not moved since release_build.py (otherwise, run release_build.py again).
  2. Sanity tests: javac sanity check on the local release zip; Maven sanity check on ~/.m2.
  3. Run allTests. If CI passed on the commit the release is based on, and the release commit changes only files in docs/, the default answer is to skip it.
  4. Generate the web site from the release zip file with the generator of eisop/eisop.github.io, in /tmp/$USER/cf-release/website, and check that every internal link of its pages works; on a problem, you decide whether to continue.
  5. Check the Maven artifacts again, upload them to Maven Central, and wait until the Central Portal has validated them. Nothing is public yet; an unpublished deployment can be dropped. In test mode, the artifacts are only checked, and the script stops here.
  6. Push master and the tag to GitHub, atomically. This is irreversible.
  7. Publish the Maven artifacts on Maven Central. This is irreversible.
  8. Post the GitHub release, with both zip files attached and the changelog section as its description, with gh release create; by hand if you decline or it fails. The daily update of the web site shows it.
  9. Check that the files attached to the GitHub release are the ones that were built.
  10. Publish the web site with the "Publish website" workflow, and wait until https://eisop.github.io/cf/ shows the release.
  11. Wait until Maven Central has published the release, and write the announcement e-mail, with the release's changelog section, to /tmp/$USER/cf-release/announcement-VERSION.txt, for you to send.
  12. Open a pull request, after you confirm, that sets releaseVersion to the next release and adds its changelog section. Renovate updates the Checker Framework version in docs/examples once the release is on Maven Central.
release_utils.py Utility methods used in both release_push and release_build.
sanity_checks.py Contains methods to run various sanity checks. These methods are called from release_push.py
javac-sanity-check.sh Runs the Nullness Checker of an unpacked release on NullnessExampleWithWarnings.java and checks the expected errors. Called by sanity_checks.py and by checker/bin-devel/test-release.sh.
checker/bin-devel/test-release.sh Run in CI. Runs the steps of the release build that need no credentials, so that a problem is found by a pull request rather than during a release.
release_vars.py Global variables and the command runners used by the other scripts: the release directory, the repositories, the version, and the Gradle options of the release.
release.gradle In the top-level directory of the repository. It defines releaseVersion and the Gradle tasks that the release scripts call: updateVersionNumbers, which writes the new version and date into the documentation and fails if a file it rewrites has moved; and updateCopyMavenExample. The zip task, which creates the release zip file, is in build.gradle.

Changelog Guidelines

Each pull request adds its changelog entry, and the numbers of the issues it closes, to the section of the next release; see docs/developer/README-eisop.md. Before releasing, check that there aren't typos or spelling errors, and that the changelog obeys the guidelines below. release_build sets the release date, and lists the issues closed since the last release that the changelog does not name.

Content Guidelines

  • Only (and all) changes that affect users (including type system developers) go into the changelog. If a change is breaking, no matter how small, mention it.
  • Even if some code has been committed to the repository, don't announce the feature until it has been documented in the manual.
  • Checker Framework:
    • List all issues (in issue trackers) resolved since the previous release: previous release, issues query, current changelog.
    • Ensure the changelogs reflect version control commits since the last release, via the command line:
      cd $CHECKERFRAMEWORK && git log --name-status `git describe --abbrev=0 --tags --match 'checker-framework-*'`..
      or via GitHub Checker Framework commit logs.
    • Ensure the changelogs reflect changes to the manual since the last release, via the command line:
      cd $CHECKERFRAMEWORK && git diff -w `git describe --abbrev=0 --tags --match 'checker-framework-*'` docs/manual
  • Annotation File Utilities:
    • The changes of the Annotation File Utilities are listed in the Checker Framework changelog. The release also has an Annotation File Utilities zip, annotation-file-utilities-VERSION.zip, and a Maven artifact, io.github.eisop:annotation-file-utilities.
    • Ensure the changelog reflects version control commits since the last release, via the command line:
      cd $CHECKERFRAMEWORK && git log --name-status `git describe --abbrev=0 --tags --match 'checker-framework-*'`.. -- annotation-file-utilities
    • Ensure the changelog reflects changes to the manual since the last release, via the command line:
      cd $CHECKERFRAMEWORK && git diff -w `git describe --abbrev=0 --tags --match 'checker-framework-*'` docs/annotation-file-utilities/annotation-file-utilities.html

Style Guidelines

  • Changes are written from the user's perspective. Don't include implementation details that users don't care about.
  • To be consistent, write in the past tense (e.g. "Added option for verbose error messages").
  • Lines should not exceed 100 characters.
  • Break the different programs into their own sections. See notes on release 1.7.0 and 1.5.0 for an example. Tools should have their own section within the Checker Framework release notes (excluding issue fixes from the issue tracker).
  • Be specific. Don't write something like "added a few options to Eclipse plugin". Do write "added options to the Eclipse plugin to include stub files, ignore warnings, and show verbose output."

Backing Out an Uncommitted Release

Two steps cannot be reverted: the push of master and the tag to GitHub (release_push step 6), and publishing to Maven Central (release_push step 7).

If you have executed either of those and then realized there is a breaking error, you should do another release.

Manual Steps to Back Out a Release

  • Before release_push step 6
    Nothing is on GitHub yet. Delete the build clone (build/checker-framework), or rerun release_build.py, which resets it.
  • After release_push step 6
    The release is on GitHub. If release_push stopped, run it again: it skips the steps that are done, and continues with the others. To abandon the release, make another one.
  • Drop the deployment from Central
    If the artifacts were uploaded but the deployment was not published, drop it (do NOT publish it) at https://central.sonatype.com/publishing/deployments.

Future Improvements

Below is a roughly priority-ordered list of future improvements.

More Sanity Checks

There are likely more sanity checks we might want to run during the release process. One such example would be running the tutorial from the command line.

Tasks:

  • Implement one of the sanity checks mentioned in this section.
  • Add your sanity check to the appropriate location in the release_push script.
  • Update this document to reflect the new steps.

Sanity Checks:

  • Run tutorial sanity check automatically via command line.

Option Parsing

There is currently some primitive option parsing written into the release scripts. We should use Python's built-in option parsing library. There are multiple built-in libraries. Please use the latest one.

Tasks:

  • Look up the latest Python parsing library.
  • Replace the option parsing in the release_build.py and release_push.py scripts with library calls.

REPL Mode

The current script is built in an imperative style with little use of object orientation. This improvement would create methods or objects that further encapsulate the current set of steps. We could then provide an easy way to execute these steps from the Python REPL. This would allow the user to execute individual steps in whatever order they saw fit from the Python REPL. This could also be used to automatically back out the current release or the ability to edit/debug the release steps more easily.

Tasks:

  • Further separate the steps of the release process.
  • Provide a default parameterization for these steps to make them easily runnable from the command line.
  • Provide a script to launch Python with these commands on its path.
  • Update this README to document the new functionality.
